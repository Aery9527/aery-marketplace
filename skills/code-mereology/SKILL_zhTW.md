# Code Mereology

設計文件負責定義模組邊界與行為；實作細節只存在於程式碼中。設計文件經確認後轉成
具體的 SBE 範例，範例直接寫成失敗的測試，再由這些測試驅動程式碼誕生。測試是規格
唯一的家，嚴禁把規格重複寫進文件。`sd-*-plan.md` 是一份用完即丟的未來工作意圖，
不是另一個規格來源。

## 階段路由

- 若任務只要求記下或檢視延後的 plan，不進入任何 phase。依照[延後變更計畫](#延後變更計畫)執行，且嚴禁載入 phase reference。
- 若使用者選擇執行某一筆延後變更條目，只把那筆條目視為 feature request，再依下方規則選擇 phase。該條目嚴禁跳過設計或測試的確認 gate。
- 若任務是建立或修改設計文件，或是把功能拆分成模組，載入 [Phase 1 — 模組化設計](references/phase1-design_zhTW.md)。
- 若已有經確認的 leaf 設計文件，且任務是定義具體 input/output 範例、挖掘 edge case，或把它們落成失敗的測試，載入 [Phase 2 — SBE 落成失敗測試](references/phase2-sbe_zhTW.md)。
- 若已有一組經確認的失敗測試，且任務是對著它做實作，載入 [Phase 3 — 實作](references/phase3-tdd_zhTW.md)。
- 若功能已實作完成，且任務是量測吞吐、延遲或資源消耗，載入 [Phase 4 — 效能驗證](references/phase4-benchmark_zhTW.md)。
- 其餘情況代表這是一項還沒有既有產出可接續的功能或模組變更，載入 [Phase 1 — 模組化設計](references/phase1-design_zhTW.md)。必須先比對上面四條；這一條只接住四條都沒接住的任務。
- 四個階段各自可獨立載入，必須依當前任務只載入需要的階段，嚴禁載入當前任務不需要的階段 reference。
- 以上五條 phase 規則是唯一的 phase reference 載入判斷依據，且必須依序比對。每份 reference 都寫明自己的產出物；依賴前一階段產出的那幾個階段，另外寫明動手之前必須驗證的狀態，因此任一階段都能在冷載入的情況下獨立執行。

## 文件模型

文件分兩層下降：描述「組裝起來的整體」的主題層，以及描述「組成它的組件」的模組層。

- `bd-<主題名稱>.md` — 組裝文件，放在 scope 根目錄下的 `docs/` 中——repository 根目錄，或 monorepo 中的 submodule 根目錄。它的主題是「組裝起來的整體在做什麼」：一項業務需求、一段架構說明、一條端到端的 data flow 都可以。必須用 Mermaid 呈現這些關係，並必須連結圖中位於它下面一層的節點。不受行數上限限制，且嚴禁下沉到下層設計文件已負責的行為細節。
- `sd-<功能名稱>.md` — 設計文件。它的主題是單一模組——組裝整體所用的一個組件。必須放在對應程式碼所在的資料夾，嚴禁集中收納到 `docs/`。`<功能名稱>` 嚴禁以 `-perf` 或 `-plan` 結尾，藉此區分設計文件與它旁邊的暫存紀錄。
- `sd-<功能名稱>-plan.md` — 放在既有 `sd-<功能名稱>.md` 旁邊的暫存延後變更計畫。它描述預計日後執行的工作，不是規格也不是文件圖節點，可以完全不被其他文件連結。它靠 plan search 被發現，不靠文件圖走訪。它不受行數上限限制，因為那條上限衡量的是設計的認知負擔，而 plan 是延後的意圖，不是設計。
- `sd-<功能名稱>-perf.md` — Phase 4 寫在被量測程式碼旁邊的效能紀錄。它記錄的是某次量測到的事實，而不是系統如何組裝，因此不屬於下方那張圖，任何階段都不會走進它。它不受行數上限限制，因為那條上限衡量的是設計的認知負擔，而它是量測結果的紀錄。
- 兩層回答的是不同問題：`bd-*.md` 回答這個系統交付什麼、各部分如何組合起來交付它；`sd-*.md` 回答單一部分做什麼、它的邊界在哪。讀者從主題進入，再往下走到組件。

在模組層內部，`sd-*.md` 本身還可以再形成一棵樹，每個節點擔任以下兩種角色之一：

- overview 角色 — 描述抽象概念，並連結到下層子模組的設計文件。嚴禁作為 Phase 2 的輸入。
- leaf 角色 — 描述單一模組自身的行為，並連結到目標程式碼。只有 leaf 才是 Phase 2 的合法輸入。

一個已經實作完成、卻沒有設計文件的模組，當有新東西依賴它時，可以先以 partial leaf 的形式進場：只描述被依賴的那個能力面，該模組其餘行為留白，讓那條依賴今天就有一份真實文件可以連，而不必先把整個模組寫完。partial 是 leaf 的屬性，不是第三種角色。它必須帶上 `code-mereology-partial` 標記並列出涵蓋了哪些能力面；凡是該標記仍排除在外的行為，嚴禁以它作為 Phase 2 的輸入。它一次長一個能力面，每一面都是真的被依賴到或被修改到才長出來，等到最後一面也寫完，標記就拿掉。

兩層合起來構成一張結構圖，圖上有兩種邊。

組成邊指向下層，說明一個節點由什麼構成，共有四種：

- root 的 `bd-*.md` 連到每一份參與該主題的 submodule `bd-*.md`
- 一份 `bd-*.md` 連到自己 scope 內每一份參與其中的 `sd-*.md`
- overview 角色的 `sd-*.md` 連到它的子層 `sd-*.md`
- leaf 角色的 `sd-*.md` 連到目標程式碼

依賴邊是橫向的，說明一個模組需要別處提供什麼能力：

- 任何 `sd-*.md` 連到每一份它所依賴其能力的 `sd-*.md`

依賴不等於組成。一份文件連到它所依賴的模組，不代表它擁有那個模組，也不會因此變成 overview。

Phase 3 會從它所實作的 leaf 沿這張圖反向回溯，因此每一條結構邊都必須是真實的 Markdown link，而不是靠語意暗示的關係。`-plan` 文件不在這張圖裡，走訪時嚴禁把它納入。

指回上層的導航連結——例如 submodule 文件提供一條回到 root 主題的路——不是結構邊。嚴禁把它當成上下層關係，否則反向回溯會繞成一個循環。

monorepo 必須採用同一模型的巢狀結構：root 的 `docs/` 放描述各 submodule 如何組裝的 `bd-*.md`——屬於更高一層的抽象；各 submodule 自己的 `bd-*.md` 則描述自己內部。submodule 的文件嚴禁把 root 層級的組裝職責重述成自己的，但可以提供一條回到 root 主題的導航連結。

## 延後變更計畫

- 只有當使用者要把某個模組變更留待日後執行時，才在既有 `sd-<功能名稱>.md` 旁建立 `sd-<功能名稱>-plan.md`。移除 `-plan` suffix 後，basename 必須與對應設計文件完全相同。
- `sd-<功能名稱>-plan.md` 可以裝下不只一筆延後變更條目。一份已交付的設計文件會隨著時間陸續收到新的變更需求，每一項都可以在輪到執行之前先被記下。條目之間要用一行空白、一行獨立的 `---`、再一行空白隔開——前後的空白行是必要的，因為緊接在一段文字下面的 `---` 會被解讀成標題底線，而不是分隔線。檔案開頭嚴禁以 `---` 起始，那在檔案最上方會被讀成 frontmatter 分隔線，而不是條目分隔線。條目必須依記錄先後附加在檔案後面，且每筆都必須自成一體：內容嚴禁依賴讀懂同一份檔案裡的另一筆條目。
- 每筆條目開頭必須先寫下它存在的原因——促成這項變更的需求或觀察——再寫 delta 本身。等到當時的情境從記憶中淡去，這個原因才是讓後續讀者判斷這筆條目是否還值得執行的依據。除了原因之外，條目必須只記錄預計發生的 delta，以及日後恢復工作所需的執行、migration 或驗證資訊。嚴禁把提案行為寫成現在的事實或已確認規格。Phase 1 必須重新驗證提案行為，Phase 2 必須重新驗證其中的具體範例。
- Plan 檔案可以完全不被其他文件連結。組裝與設計文件嚴禁只為了讓 plan 檔案可被找到就增加一條指向它的結構邊；plan 檔案本身可以為了提供 context 而往外連到現行設計或程式碼。
- 延後變更條目可以延後任意時間。檢視尚未執行的 plan 時，對 repository root 執行 [list_plans.py](scripts/list_plans.py)，再讀取每一份回報的文件，摘要它裡面每一筆條目尚未完成的工作。
- 任何 phase 選定或走訪一份 `sd-<功能名稱>.md` 時，都必須推導同目錄的 `sd-<功能名稱>-plan.md` 路徑，並在檔案存在時讀取。這項 filename lookup 讓冷載入仍能發現 plan 檔案，不需要把它加入文件圖。
- 使用者選定要執行某一筆條目時，只把那筆條目當成 feature request；同一份檔案裡的其他條目維持延後。Phase 1 必須先更新並確認對應的設計文件。Phase 2 把 SBE 凍結成失敗測試、Phase 3 完成實作之前都保留該條目。條目讓意圖可以跨越暫停，但永遠不能取代任何 phase 要求的產出物。
- 某筆條目描述的工作交付、且必要測試全綠後，必須驗證對應的 `sd-<功能名稱>.md`，以及所有受影響的組裝、上層與依賴者文件都已描述交付後的行為。驗證完成後，在同一個 change 裡刪除那筆條目；若檔案裡還留有其他條目，每一對相鄰條目之間必須剛好保留一組「空白行、---、空白行」分隔。只有當檔案裡不再留下任何條目時，才刪除整份檔案。嚴禁刪除未完成的條目；檔案不存在就表示該設計文件沒有延後工作留下。
- `-plan.md` suffix 與 `(planned)` link marker 互不相關。[list_plans.py](scripts/list_plans.py) 用來發現延後變更文件；[list_planned.py](scripts/list_planned.py) 用來發現設計文件裡尚未實現的目標承諾。

一份 `sd-<功能名稱>-plan.md` 裡有兩筆條目時，看起來像這樣：

```markdown
Why: <促成這筆條目的需求或觀察>

<預計發生的 delta，以及日後恢復工作所需的執行、migration 或驗證資訊>

---

Why: <促成下一筆條目的原因>

<它自己的 delta 與備註>
```

執行搜尋腳本時，必須從安裝後的 skill root 推導路徑，嚴禁假設固定安裝位置：

```bash
python <skill-root>/scripts/list_plans.py <repository-root>
```

## 跨階段規則

- 設計文件嚴禁出現程式碼。介面與 data view 必須以 Markdown link 指向目標程式碼，因為重複記載的細節終將與它所描述的程式碼脫節。
- 設計文件必須描述行為與注意事項。嚴禁重複演算法、控制流程或欄位層級的結構；只有當某個實作選擇實質定義了模組邊界、對外可觀察行為或相容性契約時，才可以指名該實作。
- 只要文件能把關係、data flow 或狀態轉換畫成圖，就必須使用 Mermaid。
- Mermaid 區塊必須使用剛好三個反引號與小寫的 `mermaid` 標記，嚴禁附加其他圍欄屬性，且必須從第一欄開始、前面不得有任何空白。嚴禁使用四個反引號圍欄、波浪號圍欄，也嚴禁把圖縮排放進清單項目或引用區塊，因為行數計算依賴這個標準形式。
- 單一設計文件嚴禁超過 300 計數行；`-perf` 紀錄與 `-plan` 文件不受此限。計數行 = 檔案總行數扣除所有 `mermaid` 圍欄區塊的行數（含圍欄本身）。
- 超過 300 計數行代表該模組的認知負擔過大。往下切分子模組是唯一容許的反應。嚴禁以刪減注意事項、壓縮文字敘述或把文字搬進 Mermaid 的方式壓低行數。
- 目標尚未存在的連結，必須在其緊接之後標上 `(planned)`；目標一旦存在就必須拿掉這個標記。它必須是單行的 inline link 且嚴禁帶 title，label 內嚴禁出現方括號，destination 內嚴禁出現空白或括號。嚴禁以 reference-style link 或圖片語法表達。凡是不代表真正承諾的地方，嚴禁寫出 planned link 的形狀——不可以當成 inline code 範例，也不可以出現在圖裡——因為工具只看形狀，而它看不見的承諾會被當成已經兌現的承諾。它讓讀者分得出哪些是承諾、哪些是事實，也讓負責清除它的那個階段能用搜尋一次找齊。
- 使用者必須先確認 `bd-*.md`，agent 才可往下深入它的模組；必須確認每一層 `sd-*.md`，才可往它的子層推進；並且必須在任何實作寫出來之前，確認承載凍結 SBE 的那組失敗測試。嚴禁跳過任一道 gate。
- Phase 2 與 Phase 3 是每個 leaf 各跑一輪，而不是整棵樹跑一輪。當 Phase 1 留下多個未處理的 leaf 時，由使用者決定下一個要處理哪一個。
- 標題文字由專案自行決定，但必須在該專案的文件之間保持一致：沿用同類型既有文件已經使用的標題。
- 此 skill 產出的所有設計文件都是給人類看的，因此內容盡量以 Mermaid 視覺化呈現，降低閱讀負擔。

## 階段之外的程式碼修改

不是每一次程式碼修改都循著某個階段進來。沒有循著階段進來時，同樣嚴禁讓文件停留在
描述程式碼已經不再做的事。

- 動既有程式碼之前，先看它所在的資料夾有沒有 `sd-*.md`。若這次修改的影響超出該模組，連同指向它的那些文件一起看。
- 修改之後，逐一拿它們對照程式碼現在的行為，把每一句已經不再成立的敘述修正掉。
- 若這次修改移動了模組邊界，或改變了呼叫方能觀察到的行為，只改文字是不夠的——那是設計變更，必須退回 Phase 1，嚴禁默默把文件改成配合剛寫出來的東西。
