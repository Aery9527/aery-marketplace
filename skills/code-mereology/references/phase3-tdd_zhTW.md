# Phase 3 — 實作

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把經確認的失敗測試逐一轉綠。成功的定義是：凍結集合中每個測試都通過，原本就綠的
沒有被弄壞，且被動到的設計文件仍然描述著實際建置出來的東西。

## 動手之前

- 目標 leaf 必須已有一組經使用者確認的失敗測試，由 Phase 2 產出。若不存在，嚴禁開始實作——退回 Phase 2。

## 冷載入程序

在沒有任何前置 context 的情況下載入時，必須先確立以下三件事，才可以動筆：

1. 那組失敗的測試。它們承載完整的行為規格——要做什麼，嚴禁從對話歷史推測。
2. 所屬的 leaf 設計文件，由測試檔中的 `code-mereology-leaf:` 檔頭註解指名。路徑正規化之後，每個檔案指名的必須完全相同，且必須解析到 repository 內一份真實存在、角色為 leaf、既不是 `-perf` 紀錄也不是 `-plan` 文件的設計文件。若缺少該註解、各檔指名不一致，或上述任一項檢查不通過，必須停下並退回 Phase 2，嚴禁改以「附近剛好有哪份文件」來推斷擁有者。
3. 指向這個 leaf 的文件。沿結構圖反向回溯，取出所有透過結構邊指向它的文件，分成兩類：透過組成邊指向它的是它的上層；透過依賴邊指向它的是它的依賴者。指回上層主題的導航連結、交叉引用或外部連結，兩類都不算。一個 leaf 兩類都可能有多個——一份 overview 加上不只一個主題，以及任意數量依賴它的模組。必須維護一份已造訪文件的集合，嚴禁對同一份文件處理第二次。

行為規格來自測試，文件拓撲來自上述查找。嚴禁假設單憑測試就能得知文件拓撲。

## 執行流程

1. 挑一個失敗的測試。
2. 寫出讓它轉綠的最小實作。
3. 在整組測試維持綠燈的前提下重構。
4. 從步驟 1 重複，直到凍結集合中每個測試都通過。
5. 同時執行專案既有的相關測試。本階段開始前是綠的，結束後都必須仍然是綠的。
6. 檢查 leaf 文件的介面連結是否仍解析到真實 symbol，並修正重構過程中位移的部分。
7. 逐一檢查每一份上層與每一個依賴者。上層看它畫的關係與 data flow 是否仍與實際建出來的一致，對不上就更新它的 Mermaid。依賴者看它所倚賴的契約是否仍然成立：仍成立就什麼都不改；只是 symbol 位移就修正連結。若是契約本身不再成立，嚴禁改寫依賴者去遷就它——一份被改寫成配合壞掉契約的文件，等於把破壞藏了起來。必須恢復相容性，或停下來由使用者決定那位依賴者是否需要自己走一遍 Phase 1。本步驟完成之前，必須執行依賴者自己的測試。若某份文件因此改變了它對外描述的關係，它自己的上層與依賴者也可能過時，對那份文件重複本步驟。各條路徑分別往外走，其中一條停下不影響其他條。實作只動了 leaf 內部、沒有改變它對外的邊界時，第一層檢查完就會結束。

## 規則

- 嚴禁為了讓測試通過而修改測試。看起來不對的測試屬於 Phase 2 的決策，不是 Phase 3 可以動手的地方。
- 嚴禁以 skip、停用或刪除測試的方式達成綠燈。
- 實作只能做到凍結測試與設計文件所要求的範圍。把邏輯寫成通則是應該的——測試給 `add(1, 1) == 2`，實作就該寫成兩數相加，而不是把答案寫死。但嚴禁順手加上兩者都沒要求、而呼叫方能察覺的新行為：那種行為沒有測試釘住，也沒有通過 Phase 2 的 gate。
- 嚴禁以弄壞原本就能運作的行為來換取綠燈。
- 若實作過程中發現設計文件有誤，必須停下並退回 Phase 1。放任程式碼與文件默默分歧，正是此 skill 要防止的失敗。
- 實作所依賴的 partial leaf——也就是帶有 `code-mereology-partial` 標記的那一份——是例外。若對著它實作的過程中，發現它寫的契約與既有程式碼不符，那是一份「既有事實紀錄」的記載錯誤，必須直接依程式碼修正，且嚴禁為此退回 Phase 1。步驟 7「嚴禁改寫依賴者去遷就壞掉的契約」那條規則不適用於它，因為它是被依賴的那一份文件，不是依賴者。嚴禁把這次修正擴大成描述標記仍然排除在外的那些行為。
- 接著必須檢查這次修正推翻了什麼。正在實作的那份 leaf，當初是依「partial leaf 所宣稱的契約」做設計、也是依它凍結測試的。若修正後的契約打破了其中任何一邊，必須停下並把選擇權交給使用者：是把設計退回 Phase 1，還是把凍結測試退回 Phase 2。嚴禁把這段落差在實作裡自行吸收——那會讓文件與測試都停留在描述一個從未存在過的契約。
- 嚴禁把實作細節回填到設計文件。細節唯一該存在的地方是程式碼。

## 產出物

- 一份讓凍結集合中每個測試都轉綠的實作，且沒有任何測試被 skip 或停用。
- 專案原本就通過的測試仍然通過。
- 被動到的設計文件中每一條連結都能解析到既有目標。
- 這次回溯過程中所有被動到的上層與依賴者，都與實際建置出來的結果一致，且沒有任何依賴者還在描述程式碼已經不再遵守的契約。
- 接著詢問使用者是否要進行 Phase 4。答案可以是否，也可以延後到任何時間再進行。
