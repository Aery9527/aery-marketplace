# Phase 2 — SBE 落成失敗測試

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把一份經確認的 leaf 設計文件轉成一組失敗的測試。這些測試是 SBE 唯一的存放位置。
成功的定義是：範圍內的每個行為都被一個測試釘住，而且那個測試是因為它該失敗的理由
而失敗。

## 動手之前

以下三點都必須先驗證，不符時必須依指示退回，嚴禁硬著頭皮往下做：

- 目標 `sd-*.md` 的角色必須是 leaf。若是 overview，嚴禁對它定義 SBE——退回 Phase 1，遞迴到分支終止於 leaf 為止。
- 若目標 `sd-*.md` 帶有 `code-mereology-partial` 標記，本輪即將規格化的行為必須落在該文件已涵蓋的範圍內。若它落在標記仍排除在外的部分，必須先回 Phase 1 把那個能力面補進文件並改寫標記——被排除的能力面等於沒有描述，從沒有描述的東西推導 SBE，等於什麼都沒推導。模組其餘部分可以維持未涵蓋：每一輪只為它動到的那個能力面付出代價，而這正是當初讓這份文件得以存在的同一筆有邊界的交換。
- 使用者必須已經確認過該文件。若尚未確認，先回到 Phase 1 取得確認。

## 為什麼載體是測試

本階段寫出的測試與未實作骨架是規格，不是實作。把 SBE 寫成文件，只是重述測試已經
表達的內容，隨後必然與測試脫節。本階段結尾的 gate，就是進入開發階段前的那道 gate。

## 執行流程

1. 讀取該 leaf 設計文件，列出所有需要範例的行為。
2. 記錄當前的測試基線：執行專案既有測試，記下哪些原本就通過。已經能運作的行為不構成新的 red。
3. 只問方向性問題——那幾個答案會改變整組測試形狀的問題，例如併發存取算不算範圍內、失敗時要重試還是放棄、有沒有批次處理。嚴禁帶著使用者逐項確認 edge case；推導 edge case 是本階段自己的職責，而一長串抽象條目本來就比測試本身更難判斷。
4. 推導 edge case。推導來源：文件中的注意事項、模組邊界，以及邊界值——nil、零值、上限、空集合、重複呼叫、併發呼叫、順序性，以及每一條失敗路徑。
5. 把每個行為與 edge case 直接落成測試——一個範例一個測試——放在該專案存放「該 leaf 所擁有程式碼」對應測試的位置。具體的 input 與 output 由本階段依設計文件提案；使用者在 gate 上定案，屆時他看到的是真實的值，而不是對值的描述。
6. 建立這些測試得以編譯所需的最小骨架：型別與函式簽名，函式主體維持未實作。若目標程式碼已經存在，嚴禁重建，只擴充新行為所需的部分。
7. 把 leaf 文件的介面連結收斂到本階段剛建立的 symbol 上，取代 Phase 1 留下的規劃路徑，並拿掉它們的 `(planned)` 標記。
8. 執行整組測試，確認每個新增或變更的行為都失敗，且該失敗可歸因於受測單元本身。
9. 把失敗的測試與已收斂的 leaf 文件一併呈給使用者。範圍在這裡定案：使用者刪掉不屬於範圍的測試、修正不對的值。
10. 若有任何刪除或修正，必須同步調整測試、骨架與介面連結——把只有被刪測試才需要的 symbol 一併移除——然後重跑步驟 8 與出場檢查，並帶著實際調整出來的結果回到步驟 9。如此反覆，直到某一輪使用者不再要求任何修改為止。只有那一輪未被更動、且剛通過出場檢查的集合可以取得確認，確認即是 SBE 凍結。

## 規則

- 主動推導使用者沒提到的 edge case 是本階段的義務，而非選配。嚴禁在未對使用者提供的行為清單執行步驟 4 的情況下，就認定該清單已完整。
- 嚴禁寫下任何行為邏輯。骨架引入的每個函式主體都必須維持未實作；第一行真正的邏輯屬於 Phase 3。
- 嚴禁把 SBE 寫成文件。
- 敲定方向過程中討論的一切都是互動過程中的暫時產物。嚴禁把它們寫進任何 Markdown 或設計文件，也嚴禁讓 Phase 3 依賴它們——通過 gate 之後，失敗的測試是唯一持久的規格。
- edge case 挖掘的停止條件是使用者對整組測試的確認。取得確認之後，嚴禁在本階段內繼續追加案例；確有新案例時，必須由使用者明確決定是否重開本階段。
- 若在澄清範例的過程中發現設計文件有誤或不完整，必須退回 Phase 1，嚴禁在測試裡補洞。
- 若使用者刪掉的是設計文件明文要求的行為，而不是本階段推導出來的 edge case，那就是設計變更。必須退回 Phase 1，嚴禁默默把文件的承諾縮小。
- 把規劃連結收斂到剛建立的 symbol 上，不算重開 Phase 1——那只是把已確認的契約記錄到它真實的位址。但若建立骨架的過程反而顯示已確認的行為或模組邊界本身必須更動，就必須停下並退回 Phase 1。
- 一組 Phase 2 測試必須恰好屬於一份 leaf。若範例橫跨兩份 leaf，必須拆成各自獨立的 Phase 2 迭代，嚴禁混成一組。
- 每個測試檔都必須在檔頭註解中寫出自己所屬的 leaf，採該語言的註解語法：`code-mereology-leaf: <相對於 repository 的路徑>`。同一組 Phase 2 測試中，每個檔案寫的路徑必須完全相同，且必須解析到一份已確認的設計文件——嚴禁指向 `-perf` 紀錄或 `-plan` 文件。嚴禁改以相鄰位置推斷擁有者——資料夾一旦多出第二份 `sd-*.md`，這種推斷就會無聲失效。

## 既有程式碼的情況

- 若該 leaf 已經有實作，本階段只涵蓋正在新增或變更的行為。原本就能運作的行為必須全程維持綠燈。
- 測試在第一次執行就通過，只有在它涵蓋的是新增或變更的行為時才算缺陷。嚴禁為了讓它變紅而弱化測試。

## 出場檢查

- 涵蓋新增或變更行為的每個測試都必須失敗，且該失敗必須可歸因於受測單元缺少該行為。斷言不符是最理想的形式；某些語言對空實作強制產生的未實作 sentinel——panic、`todo`、not-implemented 錯誤——同樣算合法。
- 受測單元之外的失敗永遠不是合法的 red：編譯錯誤、缺少相依或共用 setup 出錯，都必須在通過 gate 之前修掉。多個測試因為同一個尚未存在的單元而一起失敗沒有問題；因為該單元不負責的東西而一起失敗則不行。
- 步驟 2 基線中原本通過的每個測試，都必須仍然通過。
- leaf 文件中的每一條介面連結都必須解析到現在真實存在的 symbol。對該文件執行 [list_planned.py](../scripts/list_planned.py) 必須沒有任何輸出——Phase 1 對這個 leaf 許下的承諾，現在全部兌現了。該腳本位於 `<skill-root>/scripts/`，其中 `<skill-root>` 是存放本 skill `SKILL.md` 的目錄——也就是本檔案所在 `references/` 的上一層。必須從本檔案被載入的位置推導，嚴禁寫死安裝路徑。

## 產出物

- 一組涵蓋該 leaf 所有納入範圍行為的失敗測試——凍結 SBE 唯一的持久存放位置。
- 一份函式主體全數未實作的最小骨架——只有在測試引用了先前不存在的 symbol 時才需要。若只是改變既有程式碼的行為，就不會產生骨架，那樣的 Phase 2 一樣是完整的。
- 一份介面連結已指向真實 symbol 的 leaf 設計文件，使 Phase 3 從任一方向都能找到路：從測試找到文件，或從文件找到程式碼。
- 使用者對這組失敗測試的確認。取得確認之後，才可以進入 Phase 3。
