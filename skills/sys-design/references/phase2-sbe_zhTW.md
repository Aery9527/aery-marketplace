# Phase 2 — SBE 落成失敗測試

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把一份經確認的 leaf 設計文件轉成一組失敗的測試。這些測試是 SBE 唯一的存放位置。
成功的定義是：範圍內的每個行為都被一個測試釘住，而且那個測試是因為它該失敗的理由
而失敗。

## 動手之前

以下兩點都必須先驗證，不符時必須依指示退回，嚴禁硬著頭皮往下做：

- 目標 `sd-*.md` 的角色必須是 leaf。若是 overview，嚴禁對它定義 SBE——退回 Phase 1，遞迴到分支終止於 leaf 為止。
- 使用者必須已經確認過該文件。若尚未確認，先回到 Phase 1 取得確認。

## 為什麼載體是測試

本階段寫出的測試與未實作骨架是規格，不是實作。把 SBE 寫成文件，只是重述測試已經
表達的內容，隨後必然與測試脫節。本階段結尾的 gate，就是進入開發階段前的那道 gate。

## 執行流程

1. 讀取該 leaf 設計文件，列出所有需要範例的行為。
2. 記錄當前的測試基線：執行專案既有測試，記下哪些原本就通過。已經能運作的行為不構成新的 red。
3. 針對每個行為，要求使用者給出具體的 input/output 範例。沒有範例的抽象描述屬於未定義範圍，不算規格。
4. 推導 edge case 候選。推導來源：文件中的注意事項、模組邊界，以及邊界值——nil、零值、上限、空集合、重複呼叫、併發呼叫、順序性，以及每一條失敗路徑。
5. 把候選以清單形式呈給使用者，由使用者逐項標記納入或不納入。範圍必須在任何測試寫出來之前就在清單上敲定，因為在清單上調整範圍成本低，在測試程式碼裡調整成本高。嚴禁單方面決定範圍。
6. 把標記完成的集合落成測試——一個範例一個測試——放在該專案存放「該 leaf 所擁有程式碼」對應測試的位置。
7. 建立這些測試得以編譯所需的最小骨架：型別與函式簽名，函式主體維持未實作。若目標程式碼已經存在，嚴禁重建，只擴充新行為所需的部分。
8. 把 leaf 文件的介面連結收斂到本階段剛建立的 symbol 上，取代 Phase 1 留下的規劃路徑。
9. 執行整組測試，確認每個新增或變更的行為都失敗，且該失敗可歸因於受測單元本身。
10. 把失敗的測試與已收斂的 leaf 文件一併呈給使用者。使用者的確認即是 SBE 凍結。

## 規則

- 主動推導使用者沒提到的 edge case 是本階段的義務，而非選配。嚴禁在未對使用者提供的行為清單執行步驟 4 的情況下，就認定該清單已完整。
- 嚴禁寫下任何行為邏輯。骨架引入的每個函式主體都必須維持未實作；第一行真正的邏輯屬於 Phase 3。
- 嚴禁把 SBE 寫成文件。
- 候選清單與不納入標記都是互動過程中的暫時產物。嚴禁把它們寫進任何 Markdown 或設計文件，也嚴禁讓 Phase 3 依賴它們——通過 gate 之後，失敗的測試是唯一持久的規格。
- edge case 挖掘的停止條件是候選清單全數標記完畢。測試取得確認之後，嚴禁在本階段內繼續追加案例；確有新案例時，必須由使用者明確決定是否重開本階段。
- 若在澄清範例的過程中發現設計文件有誤或不完整，必須退回 Phase 1，嚴禁在測試裡補洞。
- 把規劃連結收斂到剛建立的 symbol 上，不算重開 Phase 1——那只是把已確認的契約記錄到它真實的位址。但若建立骨架的過程反而顯示已確認的行為或模組邊界本身必須更動，就必須停下並退回 Phase 1。
- 一組 Phase 2 測試必須恰好屬於一份 leaf。若範例橫跨兩份 leaf，必須拆成各自獨立的 Phase 2 迭代，嚴禁混成一組。
- 必須讓人能單憑測試就找到所屬的 leaf 文件，判定規則如下：從這些測試所操作的程式碼資料夾往上走，取第一個含有任何 `sd-*.md` 的資料夾；若該資料夾中恰好只有一份，它就是擁有者。其餘所有情況——該資料夾中有多份設計文件、完全找不到，或測試擺放方式破壞了相鄰性——每個測試檔都必須帶上檔頭註解 `sys-design-leaf: <相對於 repository 的路徑>`，且該註解永遠優先於相鄰性判定。沒有唯一明確的擁有者，Phase 3 就無法冷載入。

## 既有程式碼的情況

- 若該 leaf 已經有實作，本階段只涵蓋正在新增或變更的行為。原本就能運作的行為必須全程維持綠燈。
- 測試在第一次執行就通過，只有在它涵蓋的是新增或變更的行為時才算缺陷。嚴禁為了讓它變紅而弱化測試。

## 清單格式

在步驟 3 到 5 敲定範圍的過程中，每個候選維持以下形狀：

- 行為 — 一句話點名這次要定義的是什麼。
- Input — 逐個欄位與其具體值。
- Output — 逐個欄位與其具體值，或回傳的錯誤。
- Edge case — 每個案例一行，採 `條件 -> 結果` 形式。

## 出場檢查

- 涵蓋新增或變更行為的每個測試都必須失敗，且該失敗必須可歸因於受測單元缺少該行為。斷言不符是最理想的形式；某些語言對空實作強制產生的未實作 sentinel——panic、`todo`、not-implemented 錯誤——同樣算合法。
- 受測單元之外的失敗永遠不是合法的 red：編譯錯誤、缺少相依或共用 setup 出錯，都必須在通過 gate 之前修掉。多個測試因為同一個尚未存在的單元而一起失敗沒有問題；因為該單元不負責的東西而一起失敗則不行。
- 步驟 2 基線中原本通過的每個測試，都必須仍然通過。
- leaf 文件中的每一條介面連結都必須解析到現在真實存在的 symbol。

## 產出物

- 一組涵蓋該 leaf 所有納入範圍行為的失敗測試——凍結 SBE 唯一的持久存放位置。
- 一份函式主體全數未實作的最小骨架——只有在測試引用了先前不存在的 symbol 時才需要。若只是改變既有程式碼的行為，就不會產生骨架，那樣的 Phase 2 一樣是完整的。
- 一份介面連結已指向真實 symbol 的 leaf 設計文件，使 Phase 3 從任一方向都能找到路：從測試找到文件，或從文件找到程式碼。
- 使用者對這組失敗測試的確認。取得確認之後，才可以進入 Phase 3。
