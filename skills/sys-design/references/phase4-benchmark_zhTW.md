# Phase 4 — 效能驗證

## 目的

確認一個已完成的功能是否達到效能目標，並留下一份基準值，讓日後的優化有可比較的
依據。成功的定義是：一個實測數字，旁邊擺著一個事先講定的目標。

## 動手之前

- 功能必須已實作完成且測試全綠。若尚未完成，先把 Phase 3 做完——對未完成的程式碼取基準值，量不到任何東西。
- 本階段為選配，可以在任何時間點進入，包含 Phase 3 結束很久之後。嚴禁把它當成每個功能的必經步驟。

## 執行流程

1. 詢問使用者這個功能是否需要 benchmark 或壓測。若答案是否，本階段就此結束。
2. 在量測之前先講定效能目標：吞吐量、延遲的百分位數，以及資源上限。沒有目標的量測無從判斷好壞。
3. 把 benchmark 或壓測寫在它所量測的程式碼旁邊。
4. 把結果記進 `sd-<功能名稱>-perf.md`，放在被量測程式碼旁邊，也就是該模組設計文件的隔壁。每一筆都必須寫上目標、日期、量測環境與數字——脫離環境的數字無法重現。新的量測一律往後追加，嚴禁覆寫舊紀錄；沒有前一次的數字，優化的成效就無從判斷。
5. 把結果對照目標呈給使用者，由使用者決定是否要進行優化。

## 規則

- 紀錄必須依此順序組織：效能目標 → 歷次量測，最新的一筆排在最後。
- 嚴禁在基準值存在之前就開始優化。
- 嚴禁在優化過程中改變對外可觀察的行為。凍結 SBE 對應的測試必須全程維持綠燈。
- 若不改變行為就無法達成目標，必須退回 Phase 1——那是設計決策，不是調校工作。

## 產出物

- 一份與被量測程式碼放在一起的 benchmark 或壓測。
- 一份 `sd-<功能名稱>-perf.md`，累積至今每一次量測，各自帶著目標、日期與量測環境。
- 使用者對是否進行優化的決定。
