# Phase 3 — 實作

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把經確認的失敗測試逐一轉綠。成功的定義是：凍結集合中每個測試都通過，原本就綠的
沒有被弄壞，且被動到的設計文件仍然描述著實際建置出來的東西。

## 動手之前

- 目標 leaf 必須已有一組經使用者確認的失敗測試，由 Phase 2 產出。若不存在，嚴禁開始實作——退回 Phase 2。

## 冷載入程序

在沒有任何前置 context 的情況下載入時，必須先確立以下三件事，才可以動筆：

1. 那組失敗的測試。它們承載完整的行為規格——要做什麼，嚴禁從對話歷史推測。
2. 所屬的 leaf `sd-*.md`。測試檔中的 `sys-design-leaf:` 檔頭註解直接指名擁有者，且永遠優先。否則從這些測試所操作的程式碼資料夾往上走，取第一個含有任何 `sd-*.md` 的資料夾；該資料夾中必須恰好只有一份，那就是擁有者。若往上走的結果是零份或多份，且沒有任何註解指名，必須停下詢問使用者，嚴禁猜測。
3. 上游文件。從該 leaf 沿文件圖反向回溯：每一份連結到它的 `sd-*.md` 與 `bd-*.md` 都是它的直接上層。一個 leaf 可能有多個直接上層——一份父層 overview，加上不只一個主題——因為一個組件本來就會服務多個組裝。

行為規格來自測試，文件拓撲來自上述查找。嚴禁假設單憑測試就能得知文件拓撲。

## 執行流程

1. 挑一個失敗的測試。
2. 寫出讓它轉綠的最小實作。
3. 在整組測試維持綠燈的前提下重構。
4. 從步驟 1 重複，直到凍結集合中每個測試都通過。
5. 同時執行專案既有的相關測試。本階段開始前是綠的，結束後都必須仍然是綠的。
6. 檢查 leaf 文件的介面連結是否仍解析到真實 symbol，並修正重構過程中位移的部分。
7. 檢查每一份直接上層是否仍然反映真實的關係與 data flow，並在實作改變了這些關係之處更新其 Mermaid。若更新某份上層文件也改變了它自己的主張，就對它的上層重複本步驟；一旦某一層不需要改動，就停止往上爬。只改動了 leaf 內部、沒有變動其邊界時，通常在第一層就會停下。

## 規則

- 嚴禁為了讓測試通過而修改測試。看起來不對的測試屬於 Phase 2 的決策，不是 Phase 3 可以動手的地方。
- 嚴禁以 skip、停用或刪除測試的方式達成綠燈。
- 必須只實作凍結測試與已確認的設計邊界所要求的內容，嚴禁加入兩者都沒要求、且對外可獨立觀察的功能。把實作一般化到超出範例的字面值是應該的；加功能不是。
- 嚴禁以弄壞原本就能運作的行為來換取綠燈。
- 若實作過程中發現設計文件有誤，必須停下並退回 Phase 1。放任程式碼與文件默默分歧，正是此 skill 要防止的失敗。
- 嚴禁把實作細節回填到設計文件。細節唯一該存在的地方是程式碼。

## 產出物

- 一份讓凍結集合中每個測試都轉綠的實作，且沒有任何測試被 skip 或停用。
- 專案原本就通過的測試仍然通過。
- 被動到的設計文件中每一條連結都能解析到既有目標。
- 這次回溯過程中所有被動到的上游文件，都與實際建置出來的結果一致。
- 接著詢問使用者是否要進行 Phase 4。答案可以是否，也可以延後到任何時間再進行。
