# Phase 1 — 模組化設計

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把一個功能需求轉成設計文件，並在過程中把功能切分成高內聚、邊界清晰的模組。成功的
定義是：文件樹的每一條分支都終止於一個經使用者確認、且 Phase 2 可直接消費的 leaf。

## sd 的角色判定

本章節只管設計文件；`bd-*.md` 不具備角色之分，而 `-perf` 紀錄根本不屬於本階段處理的範圍。必須在動筆之前先決定角色。

- 若文件描述的是多個子模組如何組裝成一個更大的概念，且其主體是連往其他設計文件的連結，角色為 overview。
- 若文件描述的是單一模組自身的行為，並連結到目標程式碼，角色為 leaf。
- 光是連到其他設計文件並不足以決定角色，要看那條連結表達什麼：連到「組成它的子模組」指向 overview；連到「它只是依賴的模組」則它仍是 leaf。
- 若它既有自己的具體行為、又由子模組組成，角色必須判為 overview，且該行為必須下推到子層的 leaf 文件。

## 落點決策

本章節只做圖的規劃——有哪些節點、節點之間有哪些邊。這裡不寫入任何東西；實際的撰寫由下方的「遞迴與 gate」負責，一次一個已確認的節點。

1. 找出對應程式碼所在——或未來將放置——的資料夾。
2. 把 `sd-<功能名稱>.md` 放在該資料夾。嚴禁把設計文件集中收納到 `docs/`。
3. 釐清每個模組屬於哪個 scope：持有其程式碼的 submodule，或單一 repo 專案中的 repository 本身。跨越多個 submodule 的功能會同時在數個 scope 中持有模組。每一份 `sd-*.md` 仍然跟著它所描述的程式碼走——嚴禁只因為功能跨 submodule 就在 root 建立 `sd-*.md`。
4. 每個 scope 把自己的組裝文件放在自己根目錄下的 `docs/`。單一 repo 的專案只會有一個這樣的目錄，位於 repository 根目錄；monorepo 則是 repository 根目錄一個，加上每個 submodule 根目錄各一個。嚴禁讓 `docs/` 出現在中間的任何層級。這裡只記下哪些 scope 還缺這個目錄；目錄本身在該 scope 第一份 `bd-*.md` 開始撰寫時才出現。
5. 在每一個持有這些模組的 scope 中，指名該模組所參與主題的 `bd-*.md`——可以是既有的一份，也可以是新的 `bd-<主題名稱>.md`，命名取自「組裝起來的整體交付了什麼」，而不是取自該模組本身。它們各自都會有一條邊指向該模組的 `sd-*.md`。一個模組參與多個主題時，每個主題都會連到它——一個組件本來就會服務多個組裝。
6. 若功能跨越多個 submodule，該主題在 repository 根目錄的 `bd-*.md` 會有邊指向每一份參與其中的 submodule `bd-*.md`，且嚴禁越過它們直接連到它們的模組。邊的對象必須是文件而不是目錄——Phase 3 會反向沿著這些邊回溯，目錄不是它能跟隨的節點。
7. 這一步的產物是一份清單：有哪些節點要寫、有哪些邊要加。把它帶進「遞迴與 gate」。

## 撰寫規則 — 組裝文件

- 必須依此順序組織內容：這個組裝交付什麼 → 關係與 data flow 圖 → 下一層節點清單，每個節點附一句話說明它在這裡扮演的角色。不適用的段落可以省略，嚴禁改變順序。
- 必須以「組裝起來的整體」為主題：一項業務需求交付了什麼、一段架構如何成立、一條端到端的 data flow 流經哪裡。讀者是為了結果而來，不是為了零件清單。
- 必須用 Mermaid 呈現這些關係，並必須連結它下面一層的節點：monorepo 中位於 repository 根目錄的 `bd-*.md` 連到每一份參與其中的 submodule `bd-*.md`，且嚴禁越過它們直接連到它們的模組；其餘的 `bd-*.md` 則連到自己 scope 內每一份參與其中的 `sd-*.md`。
- 嚴禁下沉到單一模組內部怎麼運作——那屬於它所連結的 `sd-*.md`。一份在解釋單一模組規則的 `bd-*.md`，等於是放錯位置的設計文件。
- 不受行數上限限制；300 行那條規則只約束設計文件，永遠不涵蓋 `-perf` 紀錄。

## 撰寫規則 — leaf

- 必須依此順序組織內容：職責與邊界 → 關係圖 → 介面與 data view → 注意事項。不適用的段落可以省略，嚴禁改變順序。
- 必須說明該模組做什麼、擁有什麼職責，以及刻意不承擔什麼職責。
- 必須寫出注意事項：冪等性、併發、順序性、失敗行為與各種限制。
- 當文件描述兩個以上元件之間的關係、多步驟的 data flow 或狀態轉換時，必須使用 Mermaid。沒有關係可呈現時，嚴禁硬加圖。
- 必須把每個介面與 data view 表達成指向目標程式碼的 Markdown link。程式碼尚未存在的情況見下方「介面連結」。
- 若該模組需要其他模組提供的能力，必須以 Markdown link 連到那份設計文件，並在關係圖中畫出這條依賴。嚴禁把依賴寫成組成——被依賴的模組不歸本模組所有。
- 嚴禁出現 Mermaid 以外的程式碼區塊。
- 嚴禁重複演算法、控制流程或欄位層級的結構。當某個實作選擇實質定義了模組邊界、對外可觀察行為或相容性契約時，可以指名該實作或該實作限制，但必須以連結指向它，而不是把它重述一遍。

## 撰寫規則 — overview

- 必須依此順序組織內容：這個概念是什麼 → 組裝關係圖 → 子層文件清單，每份附一句話。不適用的段落可以省略，嚴禁改變順序。
- 必須描述抽象概念，以及子模組如何組裝成這個概念。
- 必須用 Mermaid 呈現組裝關係、相依關係與 data flow。
- 必須連結每一份子層設計文件。
- 嚴禁重述已由子層文件負責的行為。

## 介面連結

- 若目標程式碼已經存在，連結必須指向實際的檔案或 symbol。
- 若目標程式碼尚未存在，該連結是規劃路徑。規劃路徑只是暫時的位置標記，不是介面定義，嚴禁把它當成介面定義使用。
- 面對規劃路徑時，本階段必須把自己限制在行為邊界、輸入與輸出語意，以及職責歸屬。精確的介面由 Phase 2 在建立最小骨架時產生，並由 Phase 2 在它的確認 gate 之前把連結收斂到真實目標。
- 每一條規劃連結都必須在其緊接之後標上 `(planned)`——`[OrderValidator](internal/order/validator.go) (planned)`——讓後續讀者分得出哪些是承諾、哪些是事實。Phase 2 收斂該連結時會拿掉這個標記。
- 執行 [list_planned.py](../scripts/list_planned.py)（路徑解析方式與上面的計數器相同）即可列出一份文件裡還沒兌現的承諾。它只認緊跟在 Markdown link 之後的標記，因此散文中出現的同一個詞永遠不會被誤判。

## 行數計算

- 計數行 = 檔案總行數扣除所有 `mermaid` 圍欄區塊的行數（含圍欄）。空行、標題、frontmatter 與純連結行一律計入。
- Mermaid 區塊必須使用剛好三個反引號與小寫的 `mermaid` 標記，且必須從第一欄開始、前面不得有任何空白。嚴禁使用四個反引號圍欄、波浪號圍欄，也嚴禁把圖縮排放進清單項目或引用區塊——計數器會把其他形式一律讀成一般文字，結果是把行數算高而不是把行數藏起來，而且大型圖表放在容器裡本來就不好讀。
- 執行本 skill 內的 [count_lines.py](../scripts/count_lines.py)，傳入一個或多個文件路徑。它會逐檔印出 `<行數>` 與路徑；遇到未關閉的 Mermaid 區塊時以非零狀態碼結束。
- 腳本位於 `<skill-root>/scripts/count_lines.py`，其中 `<skill-root>` 是存放本 skill `SKILL.md` 的目錄——也就是本檔案所在 `references/` 目錄的上一層。必須從本檔案被載入的位置推導出該路徑，嚴禁寫死任何安裝路徑：本 skill 以 plugin 形式分發，會落在宿主安裝它的任何位置。

```bash
python <skill-root>/scripts/count_lines.py path/to/sd-feature.md
```

- 每次撰寫與每次修改之後都必須重新計數。

## 切分程序

當文件超過 300 計數行時觸發。

1. 嚴禁以刪減注意事項、壓縮文字敘述或把文字搬進 Mermaid 的方式壓低行數。切分模組是唯一容許的反應。
2. 依職責與 data flow 邊界找出切縫——把因相同理由而變動的內容歸為同一組。
3. 把該文件升格為 overview 角色：保留抽象的組裝描述與連結，並把每一組內容移到各自程式碼資料夾中的子層 `sd-*.md`。
4. 對每一份子層文件遞迴回到本階段。

## 升格的生命週期

若被升格的文件先前已經通過 Phase 2 與 Phase 3，其既有測試與程式碼依然有效，必須重新
掛載到現在擁有它們的那一份子層 leaf。單純的升格嚴禁觸發任何測試或實作的重寫。

## 遞迴與 gate

沿規劃好的圖由上往下走，一次處理一個節點。所有的撰寫都發生在這裡，且嚴禁跑在確認前面。

1. 在 `bd-*.md` 節點上，撰寫或更新它，包含指向規劃中子節點的那些邊。目標文件尚未存在的邊，必須標上同樣的 `(planned)` 標記。
2. 把該文件呈給使用者並取得確認。成果與組裝關係對不對，只有使用者知道，因此在取得確認之前，嚴禁撰寫任何子節點。一個模組參與多個主題時，就有多份 `bd-*.md` 要確認，且每一份各自確認。
3. 下降到每一份子層 `bd-*.md`，從步驟 1 重複，直到下面的節點是模組而不是主題為止。
4. 在 `sd-*.md` 節點上，撰寫它並計算行數；若超過上限，必須執行切分程序。
5. 把該文件呈給使用者並取得確認。在取得確認之前，嚴禁撰寫任何子層文件。
6. 下降到每一份子層 `sd-*.md`，從步驟 4 重複。
7. 當某節點的計數行不超過 300，且描述的是具體模組行為而非組裝關係時，停止下降。該節點即為 leaf。
8. 每寫完一個節點就更新它的 Mermaid，並把目標已經存在的那些邊上的 `(planned)` 標記拿掉。

## 產出物

- 一份或多份 `sd-*.md`，且每一份都在自己那一層取得使用者確認。
- 路徑上每一份 `bd-*.md` 都已更新連結與 Mermaid，並逐一節點取得使用者確認。
- 路徑上任何一條邊都不再帶有 `(planned)` 標記——每一個規劃中的節點都已存在。用 `list_planned.py` 驗證：指向 `.md` 文件的項目必須已經消失，指向程式碼的項目則會留到 Phase 2 把介面建出來為止。
- 每一條分支都終止於 leaf，使 Phase 2 具備合法輸入。
