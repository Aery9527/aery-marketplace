# Phase 1 — 模組化設計

`bd-*.md` 與 `sd-*.md` 兩層的概念定義，見 [文件模型](../SKILL_zhTW.md)。

## 目的

把一個功能需求轉成設計文件，並在過程中把功能切分成高內聚、邊界清晰的模組。成功的
定義是：文件樹的每一條分支都終止於一個經使用者確認、且 Phase 2 可直接消費的 leaf。

## sd 的角色判定

本章節只管 `sd-*.md`；`bd-*.md` 不具備角色之分。必須在動筆之前先決定角色。

- 若文件描述的是多個子模組如何組裝成一個更大的概念，且其主體是連往其他設計文件的連結，角色為 overview。
- 若文件描述的是單一模組自身的行為，並連結到目標程式碼，角色為 leaf。
- 若兩種描述都成立，角色必須判為 overview，且具體行為必須下推到子層的 leaf 文件。

## 落點決策

1. 找出對應程式碼所在——或未來將放置——的資料夾。
2. 把 `sd-<功能名稱>.md` 放在該資料夾。嚴禁把設計文件集中收納到 `docs/`。
3. 決定組裝的 scope。monorepo 情境下，功能完全落在單一 submodule 內時屬於該 submodule 的 scope；功能跨越多個 submodule 時屬於 repository 的 scope，而承載這種跨 submodule 組裝的是 root 的 `bd-*.md`。每一份 `sd-*.md` 仍然跟著它所描述的程式碼走——嚴禁只因為功能跨 submodule 就在 root 建立 `sd-*.md`。
4. 組裝文件放在第 3 步所決定 scope 根目錄下的 `docs/`。單一 repo 的專案只會有一個這樣的目錄，位於 repository 根目錄；monorepo 則是 repository 根目錄一個，加上每個 submodule 根目錄各一個。嚴禁讓 `docs/` 出現在中間的任何層級。該目錄若尚未存在，就建立它。
5. 決定哪一份 `bd-*.md` 該連到這個模組：該模組所參與的那個主題。若有多個主題都用到它，這些主題全都要連過來——一個組件本來就會服務多個組裝。
6. 若既有主題都涵蓋不到它，就建立 `bd-<主題名稱>.md`，命名取自「組裝起來的整體交付了什麼」，而不是取自該模組本身。
7. 加上連結，並更新該文件的 Mermaid，使新模組與其 data flow 出現在關係圖中。
8. monorepo 情境下，root 的 `bd-*.md` 必須連結到每一份參與該主題的 submodule `bd-*.md`，而不是連到 submodule 目錄——Phase 3 會反向沿著這些連結回溯，目錄不是它能跟隨的節點。

## 撰寫規則 — 組裝文件

- 必須以「組裝起來的整體」為主題：一項業務需求交付了什麼、一段架構如何成立、一條端到端的 data flow 流經哪裡。讀者是為了結果而來，不是為了零件清單。
- 必須用 Mermaid 呈現這些關係，並必須連結每一份參與其中的 `sd-*.md`。
- 嚴禁下沉到單一模組內部怎麼運作——那屬於它所連結的 `sd-*.md`。一份在解釋單一模組規則的 `bd-*.md`，等於是放錯位置的設計文件。
- 不受行數上限限制；300 行那條規則只約束 `sd-*.md`。

## 撰寫規則 — leaf

- 必須說明該模組做什麼、擁有什麼職責，以及刻意不承擔什麼職責。
- 必須寫出注意事項：冪等性、併發、順序性、失敗行為與各種限制。
- 當文件描述兩個以上元件之間的關係、多步驟的 data flow 或狀態轉換時，必須使用 Mermaid。沒有關係可呈現時，嚴禁硬加圖。
- 必須把每個介面與 data view 表達成指向目標程式碼的 Markdown link。程式碼尚未存在的情況見下方「介面連結」。
- 嚴禁出現 Mermaid 以外的程式碼區塊。
- 嚴禁重複演算法、控制流程或欄位層級的結構。當某個實作選擇實質定義了模組邊界、對外可觀察行為或相容性契約時，可以指名該實作或該實作限制，但必須以連結指向它，而不是把它重述一遍。

## 撰寫規則 — overview

- 必須描述抽象概念，以及子模組如何組裝成這個概念。
- 必須用 Mermaid 呈現組裝關係、相依關係與 data flow。
- 必須連結每一份子層設計文件。
- 嚴禁重述已由子層文件負責的行為。

## 介面連結

- 若目標程式碼已經存在，連結必須指向實際的檔案或 symbol。
- 若目標程式碼尚未存在，該連結是規劃路徑。規劃路徑只是暫時的位置標記，不是介面定義，嚴禁把它當成介面定義使用。
- 面對規劃路徑時，本階段必須把自己限制在行為邊界、輸入與輸出語意，以及職責歸屬。精確的介面由 Phase 2 在建立最小骨架時產生，並由 Phase 2 在它的確認 gate 之前把連結收斂到真實目標。
- 每一條規劃連結都必須在文件中標記為未收斂，讓後續讀者分得出哪些是承諾、哪些是事實。

## 行數計算

- 計數行 = 檔案總行數扣除所有 `mermaid` 圍欄區塊的行數（含圍欄）。空行、標題、frontmatter 與純連結行一律計入。
- Mermaid 區塊必須使用剛好三個反引號與小寫的 `mermaid` 標記，嚴禁使用四個反引號或波浪號圍欄——計數器會把其他形式一律當成一般文字。
- 執行本 skill 內的 [count_lines.py](../scripts/count_lines.py)，傳入一個或多個文件路徑。它會逐檔印出 `<行數>` 與路徑；遇到未關閉的 Mermaid 區塊時以非零狀態碼結束。

```bash
python <skill>/scripts/count_lines.py path/to/sd-feature.md
```

- 每次撰寫與每次修改之後都必須重新計數。

## 切分程序

當文件超過 300 計數行時觸發。

1. 嚴禁以刪減注意事項、壓縮文字敘述或把文字搬進 Mermaid 的方式壓低行數。切分模組是唯一容許的反應。
2. 依職責與 data flow 邊界找出切縫——把因相同理由而變動的內容歸為同一組。
3. 把該文件升格為 overview 角色：保留抽象的組裝描述與連結，並把每一組內容移到各自程式碼資料夾中的子層 `sd-*.md`。
4. 對每一份子層文件遞迴回到本階段。

## 升格的生命週期

若被升格的文件先前已經通過 Phase 2 與 Phase 3，其既有測試與程式碼依然有效，必須重新
掛載到現在擁有它們的那一份子層 leaf。單純的升格嚴禁觸發任何測試或實作的重寫。

## 遞迴與 gate

1. 撰寫或更新該主題的 `bd-*.md`，然後呈給使用者並取得確認。成果與組裝關係對不對，只有使用者知道，因此在取得確認之前，嚴禁往下深入任何模組。
2. 撰寫一份 `sd-*.md`。
3. 計算行數；若超過上限，必須執行切分程序。
4. 把該文件呈給使用者並取得確認。在取得確認之前，嚴禁往下層推進。
5. 下降到每一份子層文件，從步驟 2 重複。
6. 當某節點的計數行不超過 300，且描述的是具體模組行為而非組裝關係時，停止下降。該節點即為 leaf。

## 產出物

- 一份或多份 `sd-*.md`，且每一份都在自己那一層取得使用者確認。
- 相關的 `bd-*.md` 已更新連結與 Mermaid，並取得使用者確認。
- 每一條分支都終止於 leaf，使 Phase 2 具備合法輸入。
