# Claude Code Bridge

## Purpose

Run Claude Code from inside Codex. The bridge wraps the local `claude` CLI, so
it reuses the Claude Code installation, authentication and configuration
already on this machine. Success is Claude Code's own output returned to the
user verbatim, with any long-running work tracked as a job.

This skill routes a request to an entry point. It MUST NOT review code, write a
fix, or summarise Claude Code's output itself.

## Trigger Conditions

- The user asks Claude, or Claude Code, to review, challenge, investigate, fix,
  or continue work.
- The user names one of the commands listed under [Entry Points](#entry-points).
- The user asks about a running or finished Claude job.
- The user asks how to install, authenticate or configure this bridge.

## Rules

- MUST return the runtime's stdout to the user exactly as-is. MUST NOT
  paraphrase, summarise, or add commentary before or after it.
- MUST NOT act on findings a review reports. Fixing is a separate request the
  user has to make.
- MUST NOT describe `/claude-review` as sandboxed or read-only. The built-in
  reviewer inspects the repository itself and therefore runs with shell access.
  Only `/claude-adversarial-review` runs in a session that cannot write.
- MUST repeat the `Scope` and `Evidence` lines a review printed rather than
  restating the result as covering the whole repository. On
  `/claude-adversarial-review` those lines describe what the bridge itself
  collected, read across a sequence of git commands rather than as one snapshot.
  On `/claude-review` the scope is only what was requested:
  the built-in reviewer sets its own, so MUST NOT tell the user anything was
  excluded from it.
- MUST route to `claude-rescue` rather than to a review entry point when the
  user wants work done rather than assessed.
- MUST tell the user to run `/claude-setup` when the runtime reports that
  Claude Code is missing or unauthenticated. MUST NOT attempt to work around a
  failed setup check.
- MUST offer only entry points whose command file is present under
  `codex-plugin/commands/`. A plugin can be installed while parts
  of it are still unbuilt, so an entry point listed below is a claim to check,
  not a guarantee. If the entry point the request needs is absent, MUST say the
  bridge does not provide it in this installation and MUST stop.
- MUST NOT invoke the `claude` binary directly. Every call goes through the
  installed `scripts/claude-companion.mjs` runtime (sourced from
  `codex-plugin/scripts/claude-companion.mjs`), which owns
  job tracking, state and rendering.
- MUST NOT edit anything under `codex-plugins/`. That tree is generated by
  `scripts/sync-codex-plugins.ps1` from this skill directory.

## Entry Points

Each is a Codex slash command backed by the same runtime. Command names are not
namespaced by plugin, so they carry a `claude-` prefix.

- `/claude-review` — Claude Code's built-in reviewer over the working tree, or
  over the branch against a base ref with `--base <ref>`. Not steerable and
  takes no focus text. Runs with shell access, because the reviewer collects its
  own evidence.
- `/claude-adversarial-review` — review that challenges the chosen approach, its
  tradeoffs and its assumptions. Same target selection as `/claude-review`, and
  accepts focus text after the flags. Runs in a session that registers only
  `Read`, `Glob` and `Grep`, with no shell and no MCP server.
- `/claude-rescue` — delegate an investigation, a fix, or continuation of
  earlier Claude work. Write-capable by default, and it takes no tools away.
  `--resume` continues the last Claude session a finished rescue recorded — this
  Codex session's own runs when it carries an id, the repository's otherwise.
- `/claude-transfer` — convert the current Codex transcript, or an explicit
  Codex JSONL transcript selected with `--source`, into the first turn of a new
  bridge-owned Claude session. It returns a `claude --resume` command and MUST
  be described as a handoff, not as a native history import.
- `/claude-status` — active and recent Claude jobs for the current Codex session
  when it has an identifier, or for the repository otherwise. With a job id and
  `--wait`, polls until that job finishes, until the wait times out, or until no
  process is found under the job's recorded pid.
- `/claude-result` — what a finished job recorded, reprinted without rerunning
  it: the report if it produced one, otherwise the error that stopped it.
- `/claude-cancel` — ask the active job's broker to interrupt its Claude turn.
  If no verified broker acknowledgement is available, fall back to terminating
  only a process whose arguments still identify this job's worker. The report
  states which path was used and MUST NOT claim graceful interruption when only
  the fallback ran.
- `/claude-setup` — check whether Claude Code is installed and authenticated,
  and record or clear this workspace's preference for a stop-time review.

## Decision Logic

- If the user wants an assessment of existing work and names no specific
  concern, use `/claude-review`.
- If the user wants the approach, design or tradeoffs questioned, or names a
  risk area to focus on, use `/claude-adversarial-review`.
- If the user wants code changed, a bug diagnosed, or earlier Claude work
  continued, use `/claude-rescue`. MUST NOT route work there that this session can
  finish quickly on its own — handing over a small ask costs a round trip and
  returns something this session could have written.
- If the user wants to leave Codex and continue the visible conversation in
  Claude Code, use `/claude-transfer`. MUST NOT claim that separate Codex turns
  become native Claude history.
- Both review entry points run in the foreground unless `--background` is
  passed. MUST NOT tell the user a foreground review is running in the
  background, and MUST NOT present a queued job as a finished review.
- If the user does not want to wait for a review, pass `--background` and return
  the queued report. What the run recorded is collected later with
  `/claude-result`, which is the findings only if it produced them.
- If the user asks about work already started, use `/claude-status` for progress
  and `/claude-result` for what it recorded.

## Requirements

- An installed `claude` CLI. Claude Code 2.1.205 or later is recommended: the
  bridge feature-detects protocol behaviour through the `capabilities` array on
  the stream `system/init` event, and older releases do not send it, so a
  capability such as interrupting a running job is simply unavailable there. The
  version never blocks a run.
- An authenticated Claude Code installation. The bridge uses the local CLI
  login; it holds no credentials of its own.
- Node.js 18.18 or later for the runtime scripts.
