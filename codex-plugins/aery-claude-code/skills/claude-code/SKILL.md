# Claude Code Bridge

## Purpose

Run Claude Code from inside Codex. The bridge wraps the local `claude` CLI, so
it reuses the Claude Code installation, authentication and configuration
already on this machine. A standalone invocation returns Claude Code's own
output verbatim. A collaborative review makes Claude the adversarial reviewer
while Codex verifies the findings, resolves disagreements, completes authorized
work and obtains a final review. Long-running work is tracked as a job.

## Trigger Conditions

- The user asks Claude, or Claude Code, to review, challenge, investigate, fix,
  or continue work.
- The user says "call reviewer" or asks Codex to work with a reviewer until the
  reviewed task is complete.
- The user names one of the commands listed under [Entry Points](#entry-points).
- The user asks about a running or finished Claude job.
- The user asks how to install, authenticate or configure this bridge.

## Rules

- For a standalone entry-point invocation, MUST return the runtime's stdout to
  the user exactly as-is. MUST NOT paraphrase, summarise, or add commentary
  before or after it.
- During the collaborative review workflow, intermediate Claude output is
  review evidence rather than the final response. Codex MUST inspect it,
  challenge unsupported claims, implement only agreed and authorized changes,
  and report the completed workflow itself.
- Foreground progress arrives on stderr. Treat it only as live telemetry;
  MUST NOT merge it into the final stdout or present it as Claude's findings.
- In a standalone review, MUST NOT act on the findings. In a collaborative
  review, MUST NOT implement a finding until Codex has checked its factual
  claims against the code and the finding is accepted or revised into an agreed
  correction. The user's original request still determines whether changes are
  authorized.
- MUST NOT describe `/claude-review` as sandboxed or read-only. The built-in
  reviewer inspects the repository itself and therefore runs with shell access.
  Only `/claude-adversarial-review` runs in a session that cannot write.
- MUST repeat the `Scope` and `Evidence` lines a review printed rather than
  restating the result as covering the whole repository. On
  `/claude-adversarial-review` those lines describe what the bridge itself
  collected, read across a sequence of git commands rather than as one snapshot.
  On `/claude-review` the scope is only what was requested:
  the built-in reviewer sets its own, so MUST NOT tell the user anything was
  excluded from it.
- Outside the collaborative review workflow, MUST route to `claude-rescue`
  rather than to a review entry point when the user wants Claude to do the work
  rather than assess it.
- MUST tell the user to run `/claude-setup` when the runtime reports that
  Claude Code is missing or unauthenticated. MUST NOT attempt to work around a
  failed setup check.
- MUST offer only entry points whose command file is present under
  `codex-plugin/commands/`. A plugin can be installed while parts
  of it are still unbuilt, so an entry point listed below is a claim to check,
  not a guarantee. If the entry point the request needs is absent, MUST say the
  bridge does not provide it in this installation and MUST stop.
- MUST NOT invoke the `claude` binary directly. Every call goes through the
  installed `scripts/claude-companion.mjs` runtime (sourced from
  `codex-plugin/scripts/claude-companion.mjs`), which owns
  job tracking, state and rendering.
- MUST NOT edit anything under `codex-plugins/`. That tree is generated by
  `scripts/sync-codex-plugins.ps1` from this skill directory.

## Operating Modes

- If the user explicitly invokes a slash command, run that command once under
  its command file's contract. An explicit `/claude-adversarial-review` remains
  a standalone review and does not authorize follow-up discussion or fixes.
- If the user says "call reviewer" or asks Codex to involve a reviewer through
  task completion, run the collaborative review workflow. The first Claude
  report is the start of that workflow, not its completion.
- If the user merely asks Claude for an assessment and does not request reviewer
  collaboration or task completion, use the appropriate standalone review.

## Collaborative Review Workflow

1. Run the installed companion runtime's `adversarial-review --json`
   subcommand. Preserve its target, `scopeNote`, `evidenceNote`, structured
   findings and Claude session identifier. Run collaborative turns in the
   foreground so each result can inform the next step. Before using a result,
   require a successful Claude turn, a non-empty session identifier and a
   schema-valid structured result; otherwise stop and report the reviewer
   failure as a blocker. Only a valid result with an empty findings array means
   there is no material finding.
2. Check every factual claim in every material finding line by line against the
   code and available repository evidence. MUST NOT accept a finding only
   because Claude reported it.
3. When the review has material findings, continue the same Claude session
   through the companion runtime's
   `rescue --resume-session <session-id> --read-only` subcommand. Send one
   response that covers every finding line by line:
   - If a finding is correct, provide the confirming evidence and the concrete
     correction Codex proposes.
   - If a finding is incomplete, unsupported or conflicts with repository
     evidence, provide the contrary evidence and explain the objection.
   Ask Claude to confirm, revise or withdraw each finding. A failed continuation
   or one with no usable answer is a reviewer blocker, not consensus.
4. Treat the resumed `--read-only` session as a discussion constraint, not a
   sandbox: it removes direct edit tools and workspace MCP servers, but shell
   commands can still write. Tell Claude not to modify the repository and MUST
   NOT claim that the continuation cannot write.
5. Continue while either participant has a material objection supported by new
   evidence. Consensus means Claude has answered the latest evidence and every
   material finding is confirmed with an agreed correction, revised into an
   agreed correction or explicitly withdrawn. MUST NOT infer acceptance from
   silence or claim consensus while the reviewer has not answered.
6. If the discussion repeats without new evidence and neither participant can
   reach a shared conclusion, stop the exchange and report the exact unresolved
   disagreement. MUST NOT manufacture consensus or silently choose one side.
7. After consensus, Codex MUST implement the agreed corrections when they are
   within the user's authorized task. If the original request authorized only a
   review, report the agreed corrections without editing.
8. Run verification appropriate to the changed code or document, then run a
   fresh `adversarial-review --json` of the resulting state and apply the same
   success and schema checks as step 1. If it reports a new material finding,
   repeat this workflow from factual verification.
9. Finish only when the authorized corrections are complete, relevant
   verification passes and the final review has no unresolved material finding;
   otherwise report the authority, evidence or external-state blocker that
   prevents completion.

## Collaborative Review Output

- MUST state what Codex changed and how it was verified.
- MUST state which material findings were accepted, revised or withdrawn.
- MUST repeat the final review's `scopeNote` and `evidenceNote` as `Scope` and
  `Evidence` without widening either claim.
- MUST report any unresolved disagreement or blocker. MUST NOT present a queued,
  failed or unanswered review as consensus.

## Entry Points

Each is a Codex slash command backed by the same runtime. Command names are not
namespaced by plugin, so they carry a `claude-` prefix.

- `/claude-review` — Claude Code's built-in reviewer over the working tree, or
  over the branch against a base ref with `--base <ref>`. Not steerable and
  takes no focus text. Runs with shell access, because the reviewer collects its
  own evidence.
- `/claude-adversarial-review` — review that challenges the chosen approach, its
  tradeoffs and its assumptions. Same target selection as `/claude-review`, and
  accepts focus text after the flags. Runs in a session that registers only
  `Read`, `Glob` and `Grep`, with no shell and no MCP server.
- `/claude-rescue` — delegate an investigation, a fix, or continuation of
  earlier Claude work. Write-capable by default, and it takes no tools away.
  `--resume` continues the last Claude session a finished rescue recorded — this
  Codex session's own runs when it carries an id, the repository's otherwise.
- `/claude-transfer` — convert the current Codex transcript, or an explicit
  Codex JSONL transcript selected with `--source`, into the first turn of a new
  bridge-owned Claude session. It returns a `claude --resume` command and MUST
  be described as a handoff, not as a native history import.
- `/claude-status` — active and recent Claude jobs for the current Codex session
  when it has an identifier, or for the repository otherwise. With a job id and
  `--wait`, polls until that job finishes, until the wait times out, or until no
  process is found under the job's recorded pid.
- `/claude-result` — what a finished job recorded, reprinted without rerunning
  it: the report if it produced one, otherwise the error that stopped it.
- `/claude-cancel` — ask the active job's broker to interrupt its Claude turn.
  If no verified broker acknowledgement is available, fall back to terminating
  only a process whose arguments still identify this job's worker. The report
  states which path was used and MUST NOT claim graceful interruption when only
  the fallback ran.
- `/claude-setup` — check whether Claude Code is installed and authenticated,
  and record or clear this workspace's preference for a stop-time review.

## Decision Logic

- If the user explicitly names a slash command, use its standalone contract.
- If the user asks to "call reviewer" or requests reviewer involvement through
  task completion, use the collaborative review workflow.
- If the user wants an assessment of existing work and names no specific
  concern, use `/claude-review`.
- If the user wants the approach, design or tradeoffs questioned, or names a
  risk area to focus on, use `/claude-adversarial-review`.
- If the user wants code changed, a bug diagnosed, or earlier Claude work
  continued, use `/claude-rescue`. MUST NOT route work there that this session can
  finish quickly on its own — handing over a small ask costs a round trip and
  returns something this session could have written.
- If the user wants to leave Codex and continue the visible conversation in
  Claude Code, use `/claude-transfer`. MUST NOT claim that separate Codex turns
  become native Claude history.
- Both review entry points run in the foreground unless `--background` is
  passed. MUST NOT tell the user a foreground review is running in the
  background, and MUST NOT present a queued job as a finished review.
- If the user does not want to wait, or the run is likely to outlast the active
  foreground observation window, pass `--background` and return the queued
  report. Monitor it with `/claude-status` at the interval required by the
  active agent instructions, then collect what it recorded with
  `/claude-result`; that output is findings only if the run produced them.
- If the user asks about work already started, use `/claude-status` for progress
  and `/claude-result` for what it recorded.

## Requirements

- An installed `claude` CLI. Claude Code 2.1.205 or later is recommended: the
  bridge feature-detects protocol behaviour through the `capabilities` array on
  the stream `system/init` event, and older releases do not send it, so a
  capability such as interrupting a running job is simply unavailable there. The
  version never blocks a run.
- An authenticated Claude Code installation. The bridge uses the local CLI
  login; it holds no credentials of its own.
- Node.js 18.18 or later for the runtime scripts.
